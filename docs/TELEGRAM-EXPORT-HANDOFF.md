# Передача задачи: еженедельное обновление каталога из Telegram и Google Таблицы

## Цель

Обработать новый инкрементальный экспорт Telegram-канала врачей, проверить обновления
в общественной Google Таблице «Медицина в Сербии», добавить только проверенные изменения
в каталог RuDoctors и поддерживать безопасный еженедельный процесс без публикации
неподтверждённых профилей, контактов или отзывов.

## Входные данные

1. Найти новый файл `result.json` в каталоге
   `D:\Data\Downloads\Telegram Desktop\ChatExport_<дата>\`.
2. Перед запуском проверить диапазон ID и дат. Новый экспорт должен включать
   сообщения после ID `219471`; перекрытие с предыдущим экспортом нормально.
3. Проверить Google Таблицу через `npm run fetch:sheet`.
4. Не коммитить исходный экспорт, содержимое `scripts/tg-parsed/`, `scripts/sheet-doctors.json`,
   токены, cookies и другие локальные данные.

## Обязательный порядок работы

Рабочий каталог: `D:\Projects\rudoctors\site`.

```powershell
# 1. Синхронизация и проверка Google Таблицы
npm run fetch:sheet

# 2. Обработка инкрементального дампа Telegram
$env:TG_EXPORT_PATH = 'D:\Data\Downloads\Telegram Desktop\ChatExport_<дата>\result.json'
npm run fetch:tg-export
node scripts/match-tg-reviews.mjs
node scripts/find-missing-doctors.mjs
```

`match-tg-reviews.mjs` по умолчанию работает только в dry-run и создаёт
`scripts/tg-parsed/review-match-audit.json`. Его эвристические совпадения не
являются доказательством и могут быть ложными.

Для каждого предлагаемого отзыва и каждой потенциальной новой карточки вручную
проверить:

- исходное сообщение, дату, автора и точную ссылку на Telegram;
- что речь идёт именно об этом специалисте, а не об однофамильце, пересказе или архивном редиректе;
- публичность контактов и наличие устойчивой профессиональной практики;
- квалификацию и специальность по первичному источнику (официальный сайт,
  профиль специалиста, клиника), если это новая карточка;
- отсутствие медицинских утверждений у психологов/консультантов, если их нет в
  источнике.

## Как разрешается запись

Запись отзывов разрешена только после ручного решения. В локальном, игнорируемом
файле `scripts/tg-parsed/review-approvals.json` создать только проверенные пары:

```json
[
  { "messageId": 123456, "slug": "tochnyj-slug-specialista" }
]
```

После повторной проверки выполнить:

```powershell
node scripts/match-tg-reviews.mjs --write
npm run detect:dups
npm run check
npm run build
```

`--write` намеренно откажется работать без непустого списка одобренных пар.
Не применять к карточкам результаты dry-run без такого списка. Не запускать
`npm run import:tg:write` для нового экспорта: этот сценарий использует ранее
подготовленные кандидаты, а не автоматически одобренные данные нового дампа.

## Ожидаемый результат

1. Аудит новых сообщений и кандидатов с явным решением по каждому: добавить,
   обновить существующую карточку или исключить; у каждого решения есть ссылка
   на источник.
2. В репозитории изменены только проверенные JSON-карточки и/или скрипты,
   необходимые для безопасной обработки. Нет выдуманных рейтингов, отзывов,
   биографий или контактов.
3. `npm run detect:dups`, `npm run check` и `npm run build` проходят успешно.
4. В отчёте указаны число обработанных сообщений, число обновлённых карточек,
   число добавленных карточек и оставшиеся ручные проверки.
5. Только после выполнения пунктов 1–4 запросить или использовать уже данное
   разрешение на commit/push/deploy; затем подтвердить успешный GitHub Actions
   run и открытие изменённых публичных страниц.
